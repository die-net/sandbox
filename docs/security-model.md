# Security model

What the sandbox protects, what it guarantees on each platform and which test checks each guarantee, what it doesn't do, and what's still open. [Findings](findings.md) lists the attacks that worked once. The backends are described in [linux.md](linux.md) and [macos.md](macos.md).

## Threat model

The command, everything it runs, and every server it starts are untrusted. They run as the caller's own uid, so without a sandbox they could read and change anything the caller can.

The sandbox keeps the caller's data confidential: its config, database and credentials, other sandboxes' files, and people's homes. It also keeps the command away from the caller's processes.

A uid boundary gives some things for free that a sandbox has to give instead:

- File modes, and the kernel's rules on signals and tracing.
- The biggest one: the uid is the credential that local services check through `SO_PEERCRED`. The account's systemd user manager, ssh-agent and gpg-agent accept any process of the account. So the sandbox must not reach their sockets at all.
- The kernel's per-uid state: the caller's session keyring, and the process group the caller's own processes share.

It makes no claim to hide the host or its owner from what runs inside. A sandbox can read what any account on the host can, sees the machine id, and under `NetworkHost` its traffic leaves from the host's addresses. Secrets of the host's own that file modes leave readable are the operator's to fix. `Check` warns about the usual ones (see [Limits](#limits)). On macOS the gap is wider, as [Limits](#on-macos) says.

## Principles

1. **The real alternative is no sandbox.** When a sandbox is cumbersome, people turn it off. So each platform gets the strongest isolation it can give, with no setup beyond installing packages.
2. **Backends differ, and that's fine.** macOS has no pid namespace, no cgroups and no system call filter. It still gets a deny-by-default view of files, the network and Mach services. `Probe` reports what each backend gives, and the caller logs it once. A missing piece such as a memory limit or a private loopback is reported, not refused. The kernel level is the exception: a requested level can be raised but never lowered, and a level the host can't meet is an error from `Command`.
3. **Refuse only when there's no sandbox at all.** `Probe` returns an error only when no sandbox can start, and says what to fix. The library never logs, and never decides to run unsandboxed.
4. **The operator's own boundary is a sandbox too.** A container or a systemd unit can do the job of the library's sandbox. The library's part is to report honestly what that boundary enforces: `Check` with a nil `Spec` runs the escape attempts in the caller's own context.
5. **Policy stays with the caller.** The library holds the mechanism. Which paths to cover, which kernel level to ask for, what egress to allow and what limits to set belong to the program that adopts it.
6. **Adding to the allowlist is a reviewed change.** A system call in the Linux filter or a Mach service group on macOS is added only with evidence for it, and a name the library doesn't know is refused.

## Guarantees

Each row says what holds, how, and which test tries to break it. Test names are in `*_test.go` files of this package. Where a platform can't give a guarantee, the row says so and names the test that shows the gap. A `TestGap...` test fails when the gap closes, so the docs get changed with it.

The escape tests cite these rows by the first words of the Guarantee column.

| Guarantee | Linux | macOS |
|---|---|---|

## Limits

What the sandbox doesn't do. A caller should know each of these before relying on it.

- **Abstract sockets and loopback under `NetworkHost`.** With the host's network, a sandbox reaches every abstract socket and loopback listener on the host, which have no permission check. `NetworkNone` gives a private loopback (`TestEscapeLoopbackIsPrivate`).
- **Memory that isn't a file.** `ScratchSize` bounds the sandbox's tmpfs, the only ones it can write. It doesn't bound `memfd_create`, anonymous shared memory or ordinary process memory. Only a delegated cgroup's `memory.max`, through `Cmd.CgroupFD`, does. `Rlimits` bound each process, not the sandbox.
- **Descriptors the caller hands in.** A descriptor grants what the object's owner and mode allow, whatever the open mode and the covers. Pass a pipe or a socket where that matters.
- **The mount table.** `/proc/self/mountinfo` shows where each cover and bind is. A cover hides what is under a path, not that the path exists. A caller that covers its config and state by directory shows those directories' names, not the files in them.
- **What the mount table can't show.** A btrfs snapshot directory other than `/.snapshots`, or a home that neither `/etc/passwd` nor a prefix of two homes reveals, has to be covered by name. `Check` can try a path through `.zfs/snapshot` and `.snapshots`, which finds the ones that are reachable.
- **Links the operator made.** A home or `Write` path through any link is refused. On an ostree host the caller passes `/var/home/...`, not `/home/...`.
- **Stopping a sandbox.** Cancelling `ctx`, or a `SIGTERM` or `SIGHUP` to a process that is in `Run`, reaches only bubblewrap's outer process, which doesn't pass signals on. It ends, pid 1 dies with it and kills everything inside with `SIGKILL`. The command gets no chance to save its state. Pid 1 does pass `SIGTERM` and `SIGHUP` on to the command, so a caller could send them to the pid from `Pid` for a clean stop, but no test does that yet.
- **pid reuse before kernel 6.5.** Without `SO_PEERPIDFD`, a check that looks a socket's peer up in `/proc` by pid, to see whether it is in the sandbox's pid namespace, could judge a process that took that pid in between.
- **A router's address.** A client that refuses the host's interface addresses doesn't refuse a router's public address that forwards back to the host.
- **Other architectures.** With no system call list, as on 32-bit arm, only `Kernel: open` starts, with no filter and so no `TIOCSTI` refusal. `Command` refuses the other levels before it starts bubblewrap.
- **The account's groups and the host's file modes.** Both are the operator's to get right. `Check` warns when the account has supplementary groups, and when it can read any of a short list of files no service account should: `/etc/shadow`, `/etc/gshadow`, `/etc/sudoers` and `/etc/sudoers.d`, the SSH host keys, `/etc/ssl/private`, `/etc/wireguard`, NetworkManager's `system-connections`, netplan's files, PPP's and IPsec's secrets, `/etc/krb5.keytab`, certbot's `live` and `archive`, `/etc/mysql/debian.cnf`, and the admin kubeconfigs of Kubernetes and k3s. A secret an admin puts in a world-readable file, such as a password in `/etc/fstab`, is past what a list can find.
- **Pseudoterminals.** The sandbox's own `devpts` lets it open ptys, which the kernel's own limit bounds, not the sandbox's.

### On macOS

- **No pid namespace.** The sandbox sees every process of the uid, and reads the arguments and the environment of the ones that aren't Apple's (`KERN_PROCARGS2`). It can't signal them, renice them or ask about them with `process-info`, except that `fcntl(F_SETOWN)` with `O_ASYNC` makes the kernel send them `SIGIO` and `SIGURG`, which are ignored by default.
- **The caller's environment is readable.** The caller is a process of the uid, so the command reads its environment whatever `Cmd.Env` holds. A caller must hold no secret in its environment on macOS: read it and re-exec scrubbed, or take it from a file or a descriptor. The same goes for its arguments and for every other process of the account (shells, editors, agents).
- **Teardown finds the sandbox's processes by the profile.** A process that leaves the command's group by `setpgid`, a shell's job control or `setsid`, or whose parent died, is found by the marker in the profile, ended with the sandbox and counted by `Footprint`. A fork bomb can keep ahead of the teardown's scan until it stops on its own, and nothing bounds it. `Wait` then returns `ErrSurvivors`, and `Probe` lists the gap. `RLIMIT_CPU` doesn't end a process. If the stage is itself killed with `SIGKILL`, `Wait` ends the sandbox.
- **`Loopback` and `Listen` ports are on every address.** A profile names a host only as `*` or `localhost`, which is every address the host has. So the command can bind a `Loopback` port on the LAN address or the wildcard, and under `NetworkNone` any host that can reach any address of this Mac (the LAN, a VPN, a routable IPv6 address) can connect there, as can any local process. Nothing in a profile limits the peers. Only this Mac dialing its own LAN address was seen, and no second machine was tried. A command that serves should bind `127.0.0.1`, and `PrivateLoopback` is false. A command that takes an inherited socket has no gap: a listener the caller binds on `127.0.0.1` and passes in `Spec.Files` serves with no `Loopback` port, and the command's own binds of that port on other addresses are refused (`TestEscapeInheritedListenerIsLoopbackOnly`).
- **`BroadLoopback`.** Bind, accept and dial on any port of every address the host has, TCP and UDP. Without it, only the ports `Listen` and `Loopback` name, over TCP.
- **Files of the account outside the covers are readable.** The sandbox reads with the caller's uid and groups, so a file the account owns outside the four default covers is readable whatever its mode: `/opt/homebrew/var` and `etc` (service configs and database directories, even a mode-0700 Postgres data directory), `/usr/local` on an Intel Mac, and user-owned directories under `/Library/Application Support`. That is wider than "a sandbox can read what any account on the host can". The default covers stay as they are, since nothing under those paths is clearly secret on every host. A caller that has such data names it in `Spec.Cover`.
- **`ServiceFirefox`'s Mach names are shared.** `org.mozilla.machname.*` is shared with the user's own Firefox and with every other sandbox given the group ([macos.md](macos.md#services)).
- **No system call filter.** Seatbelt filters operations, so every `Kernel` level gets the one profile, and a level of `nested` or `open` gets no more.
- **Memory and processes.** `RLIMIT_AS` is refused, `RLIMIT_NPROC` counts the whole uid and `RLIMIT_CPU` is only a signal. `Footprint` is a poll.
- **Temporary files.** `TMPDIR` is in the home, with no size cap beyond `RLIMIT_FSIZE` per file, and stays until the caller removes the home. A program that hard-codes `/tmp` is refused.
- **Unix sockets and devices.** The command can't bind a unix socket of its own or connect to any but the `Write` sockets, and it can open no device but `null`, `zero`, `random`, `urandom` and `/dev/fd/N`.
- **Directory Services.** Without `ServiceDirectory`, `getpwuid` finds nothing. With it, the command can list every account.
- **One descriptor more.** The command holds the pipe that held its profile, at end of file.
- **Version dependence.** The Mach service lists and the form of each rule that held come from running macOS 27.0.1 and 27.2.0. Apple adds and renames services between releases, and a missing one can fail silently. Run the tests, and a render, on each new release.
- **`lsopen` on the server side is untested.** See [findings.md](findings.md#launching-apps-and-urls).

## Open issues

Risks that concern the library itself, most important first.

1. **Seatbelt rules drift between macOS releases.** Every rule and service group here came from running something on macOS 27.0.1 and 27.2.0 and reading the deny log. Apple adds and renames services, and a missing one can fail without an error (Firefox exits 0 with no PNG). It already happened once: curl needed `com.apple.TrustEvaluationAgent` from 27.2 ([findings.md](findings.md#tls-needed-a-mach-service-from-272)). Which shapes of network rule hold also changed with the form of the rule ([findings.md](findings.md#a-localhost-deny-held-in-only-one-form)). The `sandbox_check` call that teardown rests on is a private-ABI trampoline, run on arm64 and on amd64 under Rosetta 2, not on native Intel hardware. Rerun the suite, a Firefox render and `TestEscapeNetworkHost` on each release.
2. **The stage runs the caller's `init` with `CAP_SYS_ADMIN` on Linux.** bubblewrap starts the caller's binary again as pid 1 in a nested user namespace with `CAP_SYS_ADMIN` and `CAP_SETPCAP`, and everything that runs before `Stage` does too: package `init` functions in the binary and its libraries. That is the adopting program's own code, not anything the sandbox runs, so a program that uses the library should keep `init` functions out of it and audit its dependencies. The capabilities don't reach the view, since the namespace is nested inside the one that owns the mounts.
3. **A fork bomb can outrun macOS teardown.** Teardown scans the account's pids and signals each match as it finds it, and counts a scan as clean only if it accounts for every pid. A single process that re-forks every millisecond is ended (`TestEscapeReforkingProcessEnds`), but a fork bomb, or enough such processes, can keep ahead of the scan until it stops on its own. Nothing bounds it: `RLIMIT_NPROC` counts the whole uid and doesn't limit a chain with one live process. `Wait` returns `ErrSurvivors` when no scan proved the sandbox empty in the five seconds allowed. No method lists the survivors, so a caller treats the host as dirty. [usage.md](usage.md#what-to-do-on-errsurvivors) says what to do.

   The teardown spends its time by why scans are unclean. When scans keep finding members and the number they find has stopped falling for a second, it gives up with the stage's report that it did, and `Wait` returns `ErrSurvivors` at once, without a budget of its own. Scans that find no member and only pids they can't account for are noise, and it keeps trying for the whole 5 seconds. `Wait` still never returns nil unless a scan proved the sandbox empty: the stage's report can only make it return the error sooner.

   The scan can also fail to settle with nothing left running. A pid that vanishes, or a new process, between the list and the read makes a scan unclean whoever's process it is, so other processes of the same account that start and exit fast enough can keep scans unclean, until the 5 seconds run out and `Wait` returns `ErrSurvivors` for a clean host. That is thousands of process exits a second with the CPUs busy: with 16 fork loops (about 6,900 forks a second) 43% to 45% of scans were clean, where 0% were before the scan remembered the processes it had cleared, excused the zombies and exiting processes of non-members, waited between scans and checked new pids first, and no teardown with the full 5 seconds gave up at up to 24 loops (the worst took 295 ms). A sandbox whose command forks that fast in its own sandbox is a way to cause it for other sandboxes of the account, at the cost of saturating the CPUs. [macos.md](macos.md#process-churn) has the measurements.
4. **bubblewrap versions tested.** The floor is 0.8. The suite passes on 0.12.0 (Debian 13, arm64 and x86_64) and on 0.9.0 (Ubuntu 24.04, arm64). Descriptor passthrough, `--info-fd` and the lifeline were first confirmed on 0.12.0 ([linux.md](linux.md#descriptor-passthrough)). Nothing has run on 0.8.x, so the floor itself is untested. Before 0.12.0, setup can follow a symlink in a mount destination's parent (CVE-2026-87766, GHSA-pxhw-h44j-8pfx). Debian 12 won't fix it, and Ubuntu 24.04 rolled its fix back. The library's rule that no mount may lie inside a directory the sandbox can write avoids it (`TestPrepare`, `TestRefusedLayouts`), and CI should run the oldest version it accepts.
5. **The outer-runtime fixes `Probe` prints are partly inferred.** The AppArmor row was verified on Ubuntu 24.04. The masked-`/proc` row, and which Docker and Podman options apply, were not run. Run bubblewrap in default Docker, rootless Podman and a hardened systemd unit before relying on those messages.
